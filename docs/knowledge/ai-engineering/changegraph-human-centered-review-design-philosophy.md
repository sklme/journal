# ChangeGraph 设计哲学：面向人类的 Agent 变更审查系统

## 为什么需要一篇设计哲学

ChangeGraph 很容易被理解成“把代码依赖关系画出来”，随后逐渐演变为另一个代码索引、仓库问答或 AI Review 产品。单独写下设计哲学，是为了在具体功能、技术路线和商业压力出现时，仍然能够回答：

- 这个产品究竟服务谁？
- 它真正解决的瓶颈是什么？
- 它应该帮助人做出什么决定？
- 哪些信息可以相信，应该相信到什么程度？
- 什么能力即使技术上可以实现，也不属于它？

设计哲学不是功能清单，而是一组长期约束。一个功能如果违背这些约束，即使看起来先进，也可能让产品偏离目标。

## 一句话定义

> ChangeGraph 是一个面向人类、服务于人与 Agent 协作编程的增量变更审查与保证工具。它把一次代码变更组织成“意图—实现—影响—证据”的可交互结构，帮助人快速理解变化，并根据风险逐级决定是否需要深入到关系、路径和源码。

定义中每个限定词都不可缺少：

- **面向人类**：首要优化对象是人的理解和判断成本，而不是 Agent 的 Token 使用量。
- **人与 Agent 协作**：它不是独立的静态分析器，而是 Agent 高速生产代码之后的人类控制面。
- **增量变更**：它审查一次变化及其后续修订，不以维护永久完整的仓库图为目标。
- **审查与保证**：它不仅解释“改了什么”，还要组织支持接受决策的证据和未解决问题。
- **风险分层**：不是所有变化都值得相同成本的源码级 Review。

## 时代判断：生产正在变廉价，理解和验证成为瓶颈

传统软件开发中，写代码本身通常占据大量时间。人既是实现者，也是最熟悉实现上下文的人，因此基于代码 Diff 的 Review 虽然低效，仍然可以工作。

Agent 改变了这个平衡：

```text
代码生产速度       快速上升
人的阅读速度       基本不变
人的责任与风险     没有消失
```

当 Agent 可以在短时间内修改几十个文件，人的主要困难不再是“怎么写”，而是：

- 它是否真的实现了需求？
- 它还改变了哪些没有被声明的行为？
- 为什么测试通过仍然可能不够？
- 哪些地方值得投入有限的审查时间？
- 连续修改之后，之前的结论还有多少有效？

因此，ChangeGraph 的基本经济学不是节省 Agent Token，而是节省稀缺的人类注意力，同时避免因为理解不足而产生错误接受。

## 四个核心目标

### 1. 降低变化理解成本

让人不必先阅读全部 Diff，便能知道一次 Agent 修改声称完成什么、实际修改什么、影响哪些链路。

### 2. 提高 Review 效率

把注意力集中在关键声明、异常路径、低置信度关系和证据缺口，而不是平均分配给每个文件和代码行。

### 3. 实现风险自适应的分层审查

允许低风险变化停留在黑盒验证，高风险或不确定变化逐步深入语义关系和源码。

### 4. 让审查结论可以增量复用

Agent 后续修改后，只让真正受影响的声明、路径、证据和人工确认失效，避免每轮从头审查。

前三个目标决定 ChangeGraph 是否有用，第四个目标决定它能否长期进入真实开发流程。

## 设计公理一：ChangeGraph 首先服务人，而不是 AI

代码图最直接的用途是帮助 AI 更快检索上下文、减少重复探索，但这不是 ChangeGraph 的主要价值。Agent 多读一些代码通常只是增加时间和 Token；人理解错误可能带来沟通返工、错误决策、线上事故和长期维护成本。

因此，产品决策的第一问应当是：

> 这个能力是否让人更快、更准确地形成对变化的判断？

如果一个功能只让 Agent 更方便，却让人面对更多节点、摘要和自动结论，它不应该成为核心界面。

这并不排斥给 Agent 提供 API。Agent 可以消费 ChangeGraph，但数据结构和交互首先应满足人的可验证性：可展开、可追溯、可质疑、可回到源码。

## 设计公理二：审查变化，而不是描绘代码库

ChangeGraph 的主要对象不是整个代码库，而是两个版本之间的一次语义变化：

```text
Baseline Revision
       │
       │ Agent modifies
       ▼
Current Revision
       │
       ▼
Semantic Change Set
```

全仓库代码关系只在解释本次影响时作为背景出现。系统首先回答：

- 新增、删除或修改了哪些行为？
- 哪些原有路径被改变？
- 哪些未修改节点可能受到影响？
- 哪些变化没有对应的需求意图？

如果默认入口是一张完整仓库图，产品很容易产生“图很丰富，但人不知道下一步看什么”的问题。

> CodeGraph 描述“系统是什么”，ChangeGraph 解释“系统这一次变成了什么”。

## 设计公理三：最小审查单位是声明，不是文件和代码行

传统 Review 使用以下结构：

```text
Pull Request
    └─ File
        └─ Line Range
            └─ Comment
```

这种结构适合定位代码，却不适合表达业务判断。ChangeGraph 的最小审查单位应当是一个可验证的变更声明，以及支持或反驳它的实现路径和证据：

```text
声明：订单关闭操作必须具有幂等性
   │
   ├─ Intent：重复执行不得重复释放库存
   ├─ Change：新增终态检查与库存释放调用
   ├─ Impact：订单状态、库存、任务调度
   ├─ Evidence：顺序重复执行测试通过
   └─ Gap：缺少并发重复执行证据
```

文件、类、函数和代码行仍然存在，但它们是声明的实现材料，而不是 Review 的最高层组织方式。

一个功能是否属于 ChangeGraph，可以用这个问题判断：

> 它是否帮助人接受、拒绝或继续调查某个变更声明？

## 设计公理四：图是解释结构，不是界面目的

“Graph”描述的是内部关系模型，不意味着默认界面必须是一张力导向图。

完整关系图通常会把确定关系、推测关系、关键路径和无关背景同时展示，最终形成视觉噪声。更合理的交互顺序是渐进披露：

```text
声明摘要
   │ 用户需要更多信息
   ▼
最小相关路径
   │ 仍存在疑问
   ▼
节点、证据与关系来源
   │ 需要实现细节
   ▼
具体源码
```

默认界面更像审查卡片：

```text
┌──────────────────────────────────────────────┐
│ 声明：重复执行不会重复释放库存                │
│ 风险：高                                      │
│ 状态：证据不足                                │
├──────────────────────────────────────────────┤
│ 实现路径                                      │
│ TimeoutJob → cancel → releaseInventory       │
│                                              │
│ ✓ 单次执行测试                                │
│ ✓ 顺序重复执行测试                            │
│ ✗ 并发重复执行测试                            │
├──────────────────────────────────────────────┤
│ [展开路径] [查看源码] [询问节点] [要求补证据] │
└──────────────────────────────────────────────┘
```

图只在路径关系本身比文字更容易理解时出现。

## 设计公理五：Review 分层是在分配风险预算

分层不是为了提供三个不同主题的页面，而是为了让审查成本与变化风险相匹配。

### 第一层：它是否工作

以黑盒和验收证据为主：

- 需求场景是否通过；
- 外部行为是否符合预期；
- 性能、安全和兼容性指标是否满足；
- 失败是否可发现、可恢复、可回滚。

低风险、易回滚、证据充分的变化可以在这一层接受。

### 第二层：它改变了什么

进入 ChangeGraph 语义层：

- 哪些行为、调用链、数据流和状态转换发生变化；
- 哪些未直接修改的模块受到影响；
- 哪些实现没有对应 Intent；
- 哪些声明没有对应 Evidence；
- 哪些关系置信度不足。

这一层可以先看概要图，再按问题展开具体路径。

### 第三层：为什么这样实现

进入源码级深入审查：

- 算法和边界条件是否正确；
- 并发、缓存和事务是否安全；
- 抽象是否清晰；
- 是否引入隐藏复杂度；
- 实现是否适合长期维护。

整个过程形成逐步升级的审查漏斗：

```text
自动验证
   │
   ├─ 低风险、证据充分、易回滚
   │       └─ 接受
   │
   └─ 风险或不确定性上升
           ▼
      ChangeGraph 语义审查
           │
           ├─ 关系清晰、影响受控
           │       └─ 接受
           │
           └─ 核心链路或证据不足
                   ▼
              源码深入审查
```

> 分层 Review 的本质不是少看代码，而是把源码级注意力留给最值得看的地方。

## 设计公理六：风险决定最低审查深度

用户可以主动选择快速、标准或深入审查，但最低深度不能完全由个人直觉决定。系统应综合以下因素给出升级建议或强制策略：

```text
Review Risk
  = 业务敏感度
  × 语义变化大小
  × 影响范围
  × 历史热点与共同变化
  × 关系不确定性
  × 证据缺口
  × 回滚难度
```

仓库可以声明路径和变化类型的最低要求：

```yaml
rules:
  - match:
      paths:
        - src/payment/**
        - src/auth/**
    minimum_review_level: deep
    require:
      - independent_verifier
      - rollback_plan

  - match:
      paths:
        - docs/**
    minimum_review_level: quick
```

风险规则的目标不是制造更多流程，而是防止高风险变化因为界面简洁而获得虚假的安全感。

## 设计公理七：源代码是实现事实，图是有版本的派生视图

ChangeGraph 不能成为代码之外的第二套绝对真相。

对于“实际实现了什么”，源代码和可重复构建产物仍然是最终事实。ChangeGraph 是针对特定 Revision 生成的解释视图，每个节点和关系都必须能够回答：

- 来自哪个版本；
- 锚定到哪段源码；
- 由什么工具或主体生成；
- 是精确事实、运行观察还是启发式推测；
- 后续修改后是否仍然有效。

```yaml
relation:
  type: may_call
  source: heuristic_analysis
  confidence: low
  revision: a83fd19
  source_anchor: src/order/OrderService.java:82
  reason: runtime_dependency_injection
```

当图与源码冲突时，系统不应悄悄选择一方，而应显示图已过期或推导失败。

## 设计公理八：不确定性是一等数据

依赖注入、反射、动态配置、消息路由和运行时扩展意味着代码关系不可能总是被静态精确恢复。ChangeGraph 不应通过隐藏不确定性来营造完整感。

至少需要区分：

```text
precise     编译器或类型系统确认
observed    在特定运行环境实际观察
heuristic   静态或历史模式推测
declared    人或 Agent 主动声明
unknown     当前无法确定
```

低置信度关系本身可能就是需要提升审查深度的风险，而不是应该被过滤掉的产品缺陷。

> 好的 ChangeGraph 不是看起来知道所有答案，而是准确表达自己知道什么、不知道什么。

## 设计公理九：解释不是证据，证据必须保留来源

Agent 可以生成很流畅的变更摘要和理由，但语言连贯不等于事实正确。ChangeGraph 必须区分：

```text
declared    人或 Agent 声明
derived     编译器或静态分析推导
observed    运行时实际观察
asserted    测试明确断言
approved    人工确认
heuristic   启发式推测
```

例如：

- “该修改不会影响人工取消”是声明；
- 原有回归测试通过是证据，但只覆盖测试表达的场景；
- 一次运行 Trace 是观测事实，但不能证明所有路径；
- 覆盖率上升是信号，但不能证明业务声明成立；
- Agent 的推理过程是解释，不是独立验证。

证据还必须绑定具体代码版本。旧 Revision 上通过的测试不应自动支持已经改变的实现路径。

## 设计公理十：实现者不能独自构成完整验证闭环

如果同一个 Agent：

```text
写代码
  → 写测试
  → 解释为什么测试充分
  → 决定可以合并
```

那么它提供的是一组来自同一认知系统、相互支持的声明。共同来源的错误假设可能同时进入实现和测试。

ChangeGraph 应记录产物的生产者和验证者：

```text
Builder Agent
    │ produces
    ▼
Implementation
    │ checked by
    ▼
Independent Verifier / Human / Deterministic Tool
```

独立性可以来自：

- 不同 Agent 和不同上下文；
- 确定性静态分析器；
- 独立生成的验收测试；
- 真实或隔离的运行环境；
- 人工源码审查。

低风险变化不必机械要求多 Agent，但高风险声明应该能够配置独立验证要求。

## 设计公理十一：审查状态必须局部失效

Agent 协作不是一次性提交，而是连续修改：

```text
ChangeGraph v1
      │ Review 反馈
      ▼
Agent 修改
      │
      ▼
ChangeGraph v2
```

v2 不应该让所有审查结果清零。系统需要计算：

- 哪些声明发生变化；
- 哪些实现路径发生变化；
- 哪些证据绑定了被修改节点；
- 哪些人工批准依赖已经失效的关系；
- 哪些结论与本轮修改无关，仍然可以保留。

例如，只修改日志不应让订单幂等性的确认失效；修改状态守卫则应重新打开相关声明和测试证据。

> ChangeGraph 不只是生成图，更要保存人的审查进度，并在事实变化时精确撤销信任。

## 设计公理十二：不建立高维护成本的第二套系统

Spec、图和证据都有过期风险。ChangeGraph 的价值不能依赖团队持续手工维护完整关系网，否则它会成为新的文档债务。

更合理的原则是：

- 从 Git、编译器索引、测试、CI 和 Trace 自动采集事实；
- 只要求人维护少量高价值 Intent 和风险策略；
- 将一次变化的审查材料绑定 Revision；
- 过期时明确失效，而不是假装继续正确；
- 完整代码库模型按需重建，变化模型持续增量更新。

Spec 也不必成为永久完整的第二真相。它首先是意图留痕和对账输入；代码记录实际实现，证据记录哪些行为得到支持，三者通过持续 reconciliation 保持足够一致。

## 设计公理十三：人保留最终判断权

ChangeGraph 可以自动推荐审查深度、发现证据缺口，甚至在低风险策略允许时自动接受，但它不应通过隐藏过程替代人的控制权。

人应该始终可以：

- 查看某个结论的来源；
- 质疑或覆盖风险判断；
- 展开关系和源码；
- 要求额外证据；
- 标记 Intent 不完整；
- 拒绝 Agent 的解释；
- 查看哪些部分从未被真正验证。

自动化的目标是减少不必要的人工操作，而不是让人失去对接受条件的理解。

## 三图结构：设计哲学的数据表达

上述原则最终可以落到三个互相关联但不能相互替代的图：

```text
意图图 Intent Graph
  “系统应该发生什么变化”
            │
            │ implements
            ▼
实现图 ChangeGraph
  “代码实际上发生了什么变化”
            │
            │ verified_by
            ▼
证据图 Evidence Graph
  “哪些行为得到测试或运行证据支持”
```

三图之间最重要的不是已有连线，而是差集：

```text
有 Intent，没有实现
    → 需求遗漏

有实现，没有 Intent
    → 范围越界或未声明变化

有实现，没有 Evidence
    → 正确性仍未得到支持

有 Evidence，没有有效实现版本
    → 证据已经过期或关联错误
```

这构成 ChangeGraph 的工作原则：

> Intent first. Evidence throughout. Reconciliation before acceptance.

## Review 完成意味着什么

“所有 Diff 都被滚动浏览过”或“所有评论都已解决”不应成为完成标准。

一个变更声明可以进入接受状态，至少需要明确：

```text
Intent 已确认
+ 实现路径已解释
+ 必要证据已提供
+ 风险要求已经满足
+ 未声明变化已经处理
+ 相关人工批准仍然有效
```

一次 Review 最终应输出可决策状态：

```text
3 个声明已接受
1 个声明证据不足
2 个未声明实现变化
1 条核心路径置信度较低
```

系统的终点不是“生成了一张图”，而是帮助人做出接受、拒绝或继续调查的决定。

## 明确的非目标

ChangeGraph 从一开始就应该拒绝以下目标：

- 不以减少 Agent Token 为首要价值；
- 不试图永久维护绝对正确的完整代码图；
- 不替代源代码和构建产物；
- 不承诺证明程序完全正确；
- 不把 Agent 推理过程当作事实证据；
- 不用测试覆盖率代替行为级证据；
- 不要求团队维护与代码同等复杂的巨型 Spec；
- 不默认展示整个代码库的关系网络；
- 不让同一 Agent 的实现、测试和解释自动形成闭环证明；
- 不对每次小修改全量重置人的审查进度；
- 不为了功能完整而掩盖低置信度和未知关系。

非目标不是能力不足的辩解，而是产品保持清晰的必要边界。

## 衡量成功的指标

ChangeGraph 不应该以图节点数、索引语言数量或节省 Token 作为核心成功指标。更有意义的指标是：

### 理解效率

- 审查者形成正确变化心智模型所需时间；
- 从打开 Review 到发现核心风险的时间；
- 需要深入源码的变更比例和原因。

### 决策质量

- 被发现的未声明变化数量；
- 被识别并补齐的证据缺口；
- 接受后逃逸缺陷与原审查声明的对应关系；
- 低置信度核心路径被人工确认的比例。

### 增量复用

- Agent 后续修改后保留的有效审查状态比例；
- 因局部失效而重新打开的声明是否准确；
- 返回审查者理解新一轮变化所需时间。

### 信噪比

- 风险提示被采纳、驳回或忽略的比例；
- 无关节点和路径造成的额外阅读成本；
- 自动生成声明被人工修正的比例。

真正需要优化的是“单位人类审查时间获得的有效保证”，而不是系统生成了多少分析结果。

## 面对新功能时的决策清单

任何新功能进入 ChangeGraph 之前，都可以回答以下问题：

1. 它降低的是人的理解成本，还是只降低 Agent 的检索成本？
2. 它帮助人判断某个声明，还是只增加更多可浏览信息？
3. 结果是否绑定源码、版本、来源和置信度？
4. 如果分析错误或过期，系统是否能明确暴露？
5. 它能否支持增量更新和局部失效？
6. 它要求团队额外维护多少信息？
7. 它提供的是声明、解释、观测还是独立证据？
8. 高风险情况下，人能否下钻到路径和源码？
9. 它是否保留 Builder 与 Verifier 的认知独立性？
10. 它最终是否让接受、拒绝或继续调查的决定更可靠？

如果一个功能无法通过这些问题，它即使适合 Code Intelligence 或 AI Reviewer，也未必属于 ChangeGraph。

## 最终宣言

ChangeGraph 不是为了让人读完更多代码，也不是为了让 AI 更像一个无所不知的 Reviewer。

它接受三个现实：

1. Agent 的生产速度会持续超过人的阅读速度；
2. 任何中间表示都可能不完整、过期或带有推测；
3. 人的注意力有限，但最终责任和判断不会因此消失。

因此，它选择：

```text
以变化而不是仓库为中心
以声明而不是代码行为审查单位
以路径而不是全景图解释影响
以证据而不是流畅解释建立信任
以风险而不是统一流程分配注意力
以局部失效而不是全量重审应对迭代
以人的理解和决定而不是 AI 的便利衡量价值
```

它最终要回答的始终是：

> 这次变化是否符合意图，风险在哪里，证据是否充分，我还需要看多深？
