# Agent 型 MCP 网关：作为第二 Agent 代理规划与执行

## 要解决的问题

工具网关可以只做代理，也可以接收一个自然语言目标，自己选择并连续调用多个底层 MCP。后者看起来能把复杂度完全藏在网关后面，但它已经不是普通协议代理，而是一个拥有模型、提示词、记忆和工具循环的第二 Agent。

采用这种架构前，需要判断复杂领域流程是否值得由独立 Agent 承担，以及双重规划、上下文复制和写操作风险是否可控。

## 核心结论

Agent 型网关的结构是：

```text
用户
  ↓
客户端主 Agent
  ↓ 自然语言目标
Agent Gateway
  ↓ 自主规划、选工具、补充步骤
多个底层 MCP
```

它适合封装稳定、复杂、跨工具的领域工作流，但不适合作为所有 MCP 调用的默认入口。主 Agent 与网关 Agent 都在理解目标和规划步骤，容易产生职责重叠。

只有当领域流程可以独立验收、内部工具很多、主 Agent 不需要观察每一个中间步骤时，第二 Agent 才可能带来明显收益。

## 核心接口

Agent 型网关通常暴露一个高层任务接口：

```json
{
  "goal": "分析 Service A 最近出现超时的原因",
  "context": {
    "time_range": "最近 30 分钟",
    "environment": "production"
  },
  "constraints": {
    "max_steps": 8,
    "max_duration_seconds": 120,
    "allow_write": false
  }
}
```

网关内部可能执行：

```text
查询上下游调用和返回码
        ↓
检查 CPU、内存和网络容量
        ↓
查询相关服务日志
        ↓
必要时读取性能分析结果
        ↓
生成根因假设和证据链
```

最终返回的不只是单个工具结果，而是计划、执行轨迹、证据和结论：

```json
{
  "status": "completed",
  "summary": "超时主要集中在一个下游依赖",
  "evidence": [],
  "tool_calls": [],
  "uncertainties": [],
  "next_actions": []
}
```

对于耗时较长的任务，接口还应支持任务 ID、状态查询、取消和过期策略，而不是让一个 MCP 请求无限等待。

## 它为什么有吸引力

### 封装领域复杂度

客户端只需表达目标，不必理解调用关系、容量、日志和性能工具之间的组合顺序。领域团队可以在网关内部维护诊断流程和评测集。

### 减少主 Agent 的工具暴露

客户端只看到少量高层 Tool，底层几十个 MCP Tool 不进入主 Agent 上下文。

### 统一中间数据处理

底层工具可能返回大量时间序列、日志和调用明细。网关可以在领域内部聚合和过滤，只把证据摘要交给主 Agent。

### 支持异步长任务

复杂诊断、巡检或变更检查可能持续几分钟。Agent 型网关可以把任务持久化，提供进度、取消和最终结果查询。

### 复用稳定工作流

如果多个客户端都要重复执行同一套跨工具流程，将领域 Agent 放在网关侧可以统一升级提示词、策略与评测，不必让每个客户端分别实现。

## 主要代价

### 双重规划

主 Agent 先理解用户需求，网关 Agent 收到目标后再次理解和拆解。两个 Agent 可能形成不同假设，甚至重复提问和重复调用工具。

### 上下文边界模糊

主 Agent 知道完整对话，网关 Agent 通常只看到截取后的目标和上下文。如果传得太少，网关容易误解；如果传入完整对话，又会复制上下文成本和敏感信息。

应定义结构化的任务上下文白名单，让主 Agent 明确选择需要传递的字段，而不是默认转发整个对话。

### 延迟和成本增加

一次用户请求可能包含：

```text
主 Agent 推理
  + 网关 Agent 推理
  + 多次底层工具调用
  + 网关总结
  + 主 Agent 再次解释
```

如果多数任务只需要调用一个查询工具，第二 Agent 的固定成本很难回收。

### 可观测性下降

主 Agent 只看到网关最终结果时，很难判断：

- 为什么选择这些工具；
- 哪个参数来自用户，哪个是网关推测；
- 中间结果是否被错误概括；
- 为什么跳过某个步骤；
- 是模型判断失败，还是底层工具失败。

### 写操作风险放大

如果网关既能规划又能执行写操作，它可能在内部连续创建、修改或发布资源。主 Agent 无法仅凭一个高层调用完成逐项确认。

### 评测责任增加

普通 Broker 主要评测召回、Schema 和执行可靠性；Agent 型网关还要评测计划质量、终止条件、证据完整性、总结准确性和不同模型版本的行为变化。

## 必要的安全边界

### 计划与执行分离

高风险任务至少拆成两个阶段：

```text
plan_task(goal)
   ↓ 返回计划、参数来源、风险和预计调用
用户或主 Agent 确认
   ↓
execute_plan(plan_id, confirmation)
```

计划需要冻结工具版本、参数和影响范围；执行阶段不能在未重新确认的情况下扩大范围。

### 显式预算

每个任务应限制：

- 最大模型轮数；
- 最大底层 Tool 调用次数；
- 最大运行时间；
- 最大返回数据量；
- 允许访问的领域；
- 是否允许写操作。

达到预算后应返回不完整状态和已有证据，不能无限自循环。

### 参数来源追踪

执行记录需要标记参数来源：

```text
user       用户明确提供
tool       来自前序工具结果
policy     来自固定策略
inferred   Agent 推断
```

关键标识、时间范围、环境和写入内容不应仅凭 `inferred` 直接执行。

### 用户身份透传

网关不能用共享高权限身份替代用户授权。底层系统仍需知道最终操作者，并按资源权限进行校验。

### 完整审计

至少记录任务输入、模型版本、提示词或计划版本、工具选择理由、参数来源、底层调用、确认记录、错误分类和最终结论。

审计记录应区分可向用户展示的执行摘要与仅供系统诊断的内部事件，并对敏感字段做最小化存储。

### 人工接管

长任务应允许主 Agent 或用户暂停、取消或接管。接管时需要返回已执行步骤、当前证据、剩余计划和可能产生的副作用。

## 适合采用的场景

- 诊断流程稳定，需要组合多个只读工具；
- 底层数据量大，需要在进入主 Agent 前进行聚合；
- 任务可以异步执行并独立验收；
- 领域团队愿意维护专用提示词、评测集和安全策略；
- 客户端种类很多，希望复用一致的领域 Agent；
- 复杂任务的比例足以覆盖第二次模型调用的成本。

## 不适合采用的场景

- 大部分请求只命中一个 MCP Tool；
- 主 Agent 需要逐步观察中间结果并动态调整方向；
- 写操作要求每一步都由用户明确确认；
- 用户意图高度依赖完整对话或本地代码上下文；
- 团队尚未建立工具注册、参数校验、审计和评测基础；
- 只是为了减少 Tool Schema，而不是为了封装复杂领域流程。

## 推荐的落地顺序

1. 先实现稳定的 Tool Registry 和执行代理；
2. 先以 Broker 模式服务主 Agent；
3. 收集真实的多工具任务轨迹；
4. 找出重复且稳定的领域工作流；
5. 只把这些工作流升级为 Agent 型能力；
6. 默认只读，验证评测和审计后再考虑有限写入；
7. 保留 Broker 接口作为调试和人工接管通道。

## 选型判断

可以用一个简单问题判断：

> 这个任务是否可以作为一个独立工单交给领域专家，只验收最终证据和结论，而不需要主 Agent 逐步参与？

如果答案是“是”，Agent 型网关可能合理；如果主 Agent 必须在每一步根据上下文做判断，更适合使用 Broker 型网关。

另一个可量化方法是统计历史轨迹：如果多工具任务具有稳定顺序、相同分支条件和一致输出契约，并且占据足够请求量，才值得为它建立独立 Agent。

## 常见错误

### 把自然语言入口等同于 Agent

只有能够自主规划、迭代调用工具并根据结果改变后续步骤的网关才是 Agent。把自然语言映射为一个固定工具调用，仍然可以是确定性的 Broker。

### 只返回最终总结

没有证据引用、调用轨迹和不确定性的总结无法可靠审计。主 Agent 至少应能检查结论来自哪些工具和数据范围。

### 让第二 Agent 共享万能权限

自主规划与高权限组合会放大误操作影响。必须保留用户身份、资源级授权和写操作确认。

### 用第二 Agent 解决 Schema 膨胀

Schema 延迟加载本身不需要生成式 Agent。应先用工具注册与 Broker 解决发现问题，再根据真实工作流决定是否增加智能层。
