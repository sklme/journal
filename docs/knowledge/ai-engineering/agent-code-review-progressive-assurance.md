# Agent 代码审查的哲学：从黑盒验证到渐进式保证

## 要解决的问题

AI Agent 正在让代码生产速度远高于人的阅读速度。如果每一行 Agent 生成的代码仍然需要人逐行理解，开发瓶颈只会从“编写代码”转移到“审查代码”。

这促使我们重新思考：人是否还需要理解 Agent 产生的全部实现？一种方向是把 Agent 当作黑盒，只提供需求、环境和验证条件；另一种方向则认为源码是长期维护的知识载体，人仍需理解关键实现，只是传统 Diff Review 已经无法承载这种理解成本。

这并不是一个非黑即白的选择。更合理的目标是：

> 用与风险相匹配的独立证据，建立对一次 Agent 变更的合理信心。

Review 不再默认等于逐行阅读代码，而是一个可以逐步升级的保证过程。

## 两种审查哲学

### 黑盒验证：只关心结果是否满足契约

在黑盒模式中，人不主动关心 Agent 如何实现，而负责：

- 定义需求、验收条件和不可破坏的性质。
- 提供运行环境、输入和权限边界。
- 建立独立测试、监控和回滚机制。
- 判断最终证据是否足够。

协作关系变为：

```text
人类定义目标、边界和风险
          ↓
Builder Agent 自主实现
          ↓
独立验证系统执行测试
          ↓
人类审查结果和证据
```

这种方法类似使用编译器、数据库引擎或外部服务：使用者不会逐行检查内部实现，而依赖契约、测试、监控和故障恢复能力。

它适合局部、可逆、可观测，而且具有强测试 Oracle 的变更，例如：

- UI 文案和低风险样式调整。
- 生成代码和机械性重构。
- 独立脚本或生命周期很短的实现。
- 有 Feature Flag、灰度和自动回滚的功能。
- 可以通过确定性输入输出完整验证的逻辑。

### 机制审查：仍然理解关键实现

代码不仅是当前可执行产物，也是未来开发者继续工作的知识载体。有些实现即使测试全部通过，人仍需要理解：

- 是否改变核心领域模型。
- 是否新增不合理的跨模块依赖。
- 是否绕过安全、权限或事务边界。
- 是否破坏幂等、状态机、并发或缓存约束。
- 是否把局部需求实现成长期架构债务。
- 是否让系统未来更难修改和排障。

认证、权限、支付、账务、数据迁移、公共协议、状态机和核心基础设施等修改通常需要机制审查。问题不在于是否理解实现，而在于如何让有限的人类注意力集中到真正重要的位置。

## 黑盒验证的根本限制

“测试通过”不等于“实现可以接受”。测试只能证明被表达和执行过的性质，未发现问题可能是因为：

- 验收条件本身不完整。
- 实现和测试对需求产生了相同误解。
- 没有覆盖安全、性能、并发和异常路径。
- 当前行为正确，但实现难以维护。
- 引入了不必要的依赖、权限或架构耦合。
- 测试只证明当前样例，没有覆盖长期不变量。

### 实现者不能成为唯一验证者

如果同一个 Agent 写代码、写测试，再解释测试为何通过，它提出的只是一组相互支持的声明，而不是独立证据。

```text
同一上下文中的 Builder
   ├─ 解释需求
   ├─ 编写实现
   ├─ 选择测试场景
   └─ 判断测试充分

共同盲区会贯穿整条链路
```

Builder 可能忠实地把同一个错误理解同时写入实现和测试，最终得到一个完全自洽但不符合真实需求的结果。

更可靠的结构需要认知独立：

```text
需求与业务约束：人类或独立规格来源
实现：Builder Agent
测试设计与反例探索：Verifier Agent
确定性验证：编译器、测试、静态检查、运行环境
风险判断：规则系统 + 人类
上线验证：监控、灰度与回滚
```

Verifier 不只是换一个进程重新运行 Builder 写的测试。它应拥有不同的目标、上下文和成功标准，主动寻找反例、遗漏条件和错误假设。确定性工具负责执行证据，人类负责判断证据是否覆盖真实风险。

## 完整 Review 的三个问题

一次 Review 可以分为三个逐步深入的问题。

### 第一层：它是否工作？

这是黑盒验证关心的问题：

- 验收测试是否通过？
- 外部行为是否满足需求？
- 性能和安全指标是否符合要求？
- 失败是否可以及时发现和恢复？
- 功能是否可以灰度、关闭或回滚？

这一层验证的是系统对外表现，但不会解释内部发生了什么。

### 第二层：它改变了什么？

这是 ChangeGraph 语义审查关心的问题：

- 增加或删除了什么业务入口？
- 改变了哪些调用链和数据流？
- 哪些模块、接口和外部系统受到影响？
- 哪些原有约束被改变？
- 哪些影响没有测试覆盖？
- 是否出现计划之外的修改？

这一层不要求人阅读全部源码，而是建立对本次变化的系统模型。

### 第三层：它为什么这样实现？

这是源码级 Review 关心的问题：

- 具体算法和边界条件是否合理？
- 异常、并发和回滚路径是否正确？
- 抽象和职责划分是否清晰？
- 是否引入隐藏复杂度和长期维护成本？
- 代码是否遵循关键领域不变量？

不是所有修改都必须进入第三层，但第一层不能证明第二层没有遗漏，第二层也不能在高风险场景完全替代第三层。

## 统一模型：渐进式保证

两种审查哲学可以统一成风险自适应的渐进流程：

```text
自动校验
   │
   ├─ 证据充分、低风险、易回滚
   │        └─ 直接接受
   │
   └─ 风险或不确定性上升
            ↓
      ChangeGraph 语义审查
            │
            ├─ 关系清晰、影响受控
            │        └─ 接受
            │
            └─ 核心链路或证据不足
                     ↓
               源码级深入审查
```

这个流程的目标不是让每次 Review 都更深入，而是安全地决定哪些代码可以不看、哪些关系需要理解、哪些位置必须读源码。

可以用一个非严格公式表达审查强度：

```text
审查强度
≈ 影响范围 × 失败代价 × 不可逆性 × 不确定性
  ───────────────────────────────────────
              验证证据强度
```

决定深度的不只是需求是否重要，还包括：

- 失败影响是否局限在明确范围。
- 失败能否立即发现。
- 数据和外部副作用是否可逆。
- 是否存在独立、可靠的验证 Oracle。
- 是否改变公共契约或核心架构关系。
- 当前区域是否具有足够的监控和历史知识。
- Agent 使用了多少启发式推断或新颖实现。

一个重要但有强隔离、灰度和回滚能力的变更，可以减少部分合并前阅读；一个看似很小却会永久修改数据、又难以监控的变更，反而应进入深入审查。

## 从审查代码转向审查声明与证据

传统 Review 的基本单位是文件和代码行。Agent 时代，更合理的基本单位是一组需要被证明的声明。

```text
声明 1：新增订单超时自动关闭能力
证据：端到端测试、TimeoutJob 节点和状态转换关系

声明 2：不会影响人工取消订单
证据：修改前后链路对照、原有回归测试

声明 3：重复执行不会重复释放库存
证据：幂等测试、状态检查和运行时 Trace

声明 4：没有改变公共接口
证据：API Schema Diff
```

Review 的核心问题从“我是否读懂每一行代码”变为：

> 这些证据是否足以支撑 Agent 对本次变更提出的声明？

如果某项声明缺少证据，再有针对性地深入相关节点、关系和源码。

### 声明需要区分类型

一份变更至少可能包含：

- **意图声明**：实现了哪个需求或验收条件。
- **行为声明**：输入、输出和副作用发生了什么变化。
- **非回归声明**：哪些原有能力不会受到影响。
- **质量声明**：性能、安全、可维护性是否满足要求。
- **运行声明**：如何发布、观测、失败恢复和回滚。

每类声明需要不同证据。单元测试可以支持局部行为，却无法单独证明公共接口未改变；代码图可以显示结构影响，却无法单独证明并发行为正确；运行时 Trace 可以证明某条路径发生过，却不能证明其他路径不存在。

## ChangeGraph 是审查升级的控制面

ChangeGraph 不只是代码可视化工具，而应组织四层信息：

```text
变更声明
  “Agent 声称自己实现了什么”

变更事实
  “源码、结构和契约实际改变了什么”

验证证据
  “哪些测试、检查和 Trace 支持这些声明”

风险与缺口
  “哪些影响尚未确认”
```

它可以在人工介入前检查：

- 修改是否只发生在低敏感路径。
- 是否改变公共接口、消息协议或数据 Schema。
- 是否新增跨模块关系。
- 是否修改持久化数据或关键状态机。
- 是否存在未覆盖的行为节点。
- Builder 的计划与最终修改是否一致。
- 测试是否由 Builder 新增并成为唯一证据。
- 是否存在大量低置信度调用关系。

没有风险信号时，人只看摘要和验证结果；出现风险时展开 ChangeGraph；图中仍有不确定性时，再进入具体源码。

## 人的角色：保证体系设计者

人不再只是代码作者或逐行检查者，而更像软件保证体系的设计者：

- 定义什么是正确。
- 定义哪些风险不可接受。
- 维护关键业务和架构不变量。
- 设计独立验证机制。
- 决定不同区域的审核敏感度。
- 判断证据是否充分。
- 对高风险变更承担最终决策责任。

人的注意力从机械阅读转向更难被自动化的部分：需求判断、系统边界、风险权衡、证据质量和长期架构。

## 可落地的五级审查

### Level 0：自动接受

适用于低风险、可回滚、具有强确定性检查的机械变更。要求自动测试通过，没有敏感路径、公共契约或持久化副作用变化。

### Level 1：结果审查

人只检查需求、验收结果、风险摘要、监控和回滚能力，不主动阅读实现。

### Level 2：ChangeGraph 审查

人检查需求到实现的映射、修改前后的业务链路、受影响模块、数据副作用、测试缺口和不确定关系，只在发现问题时进入源码。

### Level 3：源码级审查

针对核心、高风险或证据不足的变更，深入算法、异常路径、并发语义、领域约束和代码质量。

### Level 4：强化保证

极高风险变更增加多人审核、独立 Agent 复核、属性测试、安全分析、灰度、运行时监控和自动回滚，必要时使用更强的规格与证明手段。

## 适用边界

### 可以减少源码阅读的条件

- 行为具有清晰且独立的验证 Oracle。
- 失败容易发现，影响范围受控。
- 修改可快速回滚或被 Feature Flag 隔离。
- 不改变持久化数据、公共契约和核心架构。
- 验证证据来自独立角色和确定性工具。

### 必须提高理解深度的条件

- 测试难以表达完整正确性。
- 失败不可逆、难观测或影响范围未知。
- 涉及权限、资金、数据、并发和状态机。
- 改变核心抽象或新增跨边界依赖。
- Builder 与 Verifier 共享相同假设和上下文。
- 证据之间互相冲突，或依赖低置信度推断。

## 常见错误

### 把测试通过等同于实现正确

测试只覆盖已表达的性质，无法证明没有遗漏需求、安全风险或维护性问题。

### 让 Builder 完成全部自证

实现、测试和解释共享同一认知路径时，一个错误假设可能贯穿全流程。需要独立 Verifier 和确定性证据。

### 所有变更使用相同 Review 深度

统一逐行阅读无法扩展，统一黑盒接受又会放过高风险实现。审查强度必须由风险和证据共同决定。

### 把 ChangeGraph 当作新的事实源

ChangeGraph 负责聚合声明、变化、影响和证据，但图本身仍是派生信息。源码、测试、契约和运行结果保留最终解释权。

### 只在合并前建立信心

对于依赖真实环境才能验证的行为，灰度、监控和回滚属于 Review 的延伸，而不是部署后的附加工作。

## 可复用原则

1. **Review 的目标是合理信心，不是阅读覆盖率。**
2. **默认验证结果，按风险逐步理解变化和机制。**
3. **Builder 与 Verifier 保持目标和上下文上的认知独立。**
4. **把声明连接到证据，而不是接受 Agent 的自我解释。**
5. **证据强度必须与失败代价和不可逆性匹配。**
6. **ChangeGraph 用于决定在哪里深入，而不是替代源码事实。**
7. **把灰度、监控和回滚视为软件保证体系的一部分。**
8. **将人的注意力集中在需求、边界、风险和长期架构上。**
