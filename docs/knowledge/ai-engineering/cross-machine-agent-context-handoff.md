# 跨机器 Agent 上下文交接：任务状态、长期记忆与 Multica 实践

## 要解决的问题

开发工作在 Linux 开发机上进行，浏览器登录态和桌面配置却在本机。远端 Agent 遇到需要本机操作的步骤时，本机新会话通常缺少目标、已验证结论和待办细节。

可靠的交接需要把任务资料保存在会话之外，使接手者能够读取当前状态、追溯依据、完成操作并回传结果。若还希望自动启动本机 Agent，则需要执行调度和唤醒机制。

本文整理公开文档与源码核查所得的机制，示例均为通用设计。社区项目的实现依据核查于 2026-09-07；未进行跨机器部署或端到端实测，引用的主分支代码也可能继续变化。

## 核心原理：四类数据与一个执行层

| 层次 | 保存或管理什么 | 接手时怎样使用 |
| --- | --- | --- |
| 会话历史 | 原始讨论、可见工具调用和结果 | 按会话或关键词追溯细节 |
| 任务状态 | 目标、负责人、依赖、进度、验收和结果 | 按任务 ID 精确读取 |
| 长期记忆 | 可复用事实、决策、约定和排障经验 | 按标签、关键词、语义检索 |
| 原生会话数据 | 特定 Agent 工具的 transcript、恢复标识等 | 在支持且数据可用时 resume |
| 执行层 | 任务通知、领取、启动、重试、完成回报 | 让目标机器实际开始工作 |

外部记忆被检索并返回当前对话后，才成为模型这次推理可用的上下文。它通常不会修改模型权重。MCP 提供访问接口；何时读取、保存什么、如何保证任务状态准确，仍由应用和工作流决定。

```text
远端 Agent ── 写入任务与证据 ──→ 共享存储
                                    │
本机 Agent ←── 精确读取 + 按需检索 ──┘
    │
    └── 执行本机操作 ── 写回结果 ──→ 远端 Agent 继续
```

## 共享任务状态：结构化记录与精确查询

### 存储形态

小规模实现可以使用一个任务一个 JSON、YAML 或 Markdown 文件。需要并发领取和查询时，可以使用 SQLite、PostgreSQL 等数据库，把任务存为记录，把依赖和事件存为关联表。

以下是逻辑结构示例，并非某个工具的接口定义：

```json
{
  "id": "task-042",
  "project": "Project A",
  "title": "配置本机浏览器并验证测试页面",
  "status": "pending",
  "target_host": "desktop",
  "assignee": null,
  "context": "开发机服务已启动，等待浏览器验证",
  "acceptance": "页面加载成功，服务端记录到预期请求",
  "depends_on": ["task-041"],
  "result": null,
  "revision": 3
}
```

数据库可以分别保存当前状态、依赖关系、状态变更事件和产物引用。大日志与截图可以作为附件存储，任务中保存能被接手者访问的引用；只有远端本地路径的引用不能直接供本机读取。

### 检索和领取

任务检索优先使用明确条件：任务 ID、项目、目标机器、状态和未完成依赖。语义搜索可以帮助发现相关任务，但当前进度应由任务记录确认。

```text
列出本机可执行任务
    → 按 ID 读取完整任务与依赖
    → 原子领取
    → 执行并验证
    → 写回结果和完成状态
```

领取可以通过条件更新实现：

```sql
UPDATE tasks
SET assignee = 'desktop-agent',
    status = 'running',
    revision = revision + 1
WHERE id = 'task-042'
  AND status = 'pending'
  AND revision = 3;
```

只有更新成功的执行者才能开始工作。这个保证限于同一个权威数据库中的原子操作；两台离线机器各自在本地副本更新成功，并不构成全局互斥。

如果需要自动重试，还应定义领取租约、过期后的接管规则，以及如何核实上一次操作是否已产生效果。数据库状态更新本身无法保证外部操作恰好执行一次。

### Beads 的实践

Beads 将任务组织为带依赖的图。当前文档描述的是 Dolt 存储：支持版本历史、分支和合并，跨机器使用 `bd dolt push/pull` 同步。`bd ready` 查找可执行工作，`bd show` 读取详情，`bd update --claim` 领取任务。JSONL 是导出交换形态，不能据此认为当前数据库只是一份可直接覆盖的文本文件。参见 [Beads 文档](https://github.com/gastownhall/beads)。

## 共享长期记忆：正文、元数据与检索索引

### 存储形态与写入流程

长期记忆通常是一段可读文本，加上项目、标签、来源和时间等元数据。例如：

```json
{
  "id": "mem-108",
  "content": "Project A 的测试页面需要使用本机浏览器的开发代理配置。",
  "type": "environment",
  "project": "Project A",
  "host": "desktop",
  "tags": ["browser", "proxy", "testing"],
  "source_task": "task-042",
  "status": "active",
  "updated_at": "2026-09-08T09:00:00Z"
}
```

记忆可由 Agent 显式保存，也可由 hook 或独立程序从会话中提取。典型过程是：提取事实与决策，补上范围和来源，去重，处理替代关系，再保存和建立索引。安装 memory MCP 不会自动赋予它读取所有会话的能力。

存储可以拆成三部分：

| 部分 | 内容与用途 |
| --- | --- |
| 正文与元数据 | 保存知识本身、适用范围、时间和来源 |
| 全文索引 | 匹配域名、错误码、配置名等精确线索 |
| 向量索引 | 保存 embedding，查找意思相近的内容 |

Embedding 是由文本生成的数值向量。检索时计算相似度，返回的主要内容仍是正文及其来源。向量不能替代原始文本，也不能证明文本真实或仍然有效。

mcp-memory-service 的数据模型包含正文、内容哈希、标签、类型、元数据、时间戳和可选向量；存储支持 SQLite-vec、Cloudflare、Hybrid 等后端。参见 [Memory 数据模型](https://github.com/doobidoo/mcp-memory-service/blob/main/src/mcp_memory_service/models/memory.py) 和 [项目说明](https://github.com/doobidoo/mcp-memory-service)。

### 检索流程

一种可采用的混合检索流程如下，具体实现不必包含所有步骤：

```text
当前问题
    → 明确访问范围、项目与环境
    → 关键词检索 + 向量检索
    → 合并、去重与排序
    → 排除失效或被替代的记录
    → 在上下文预算内返回相关正文与来源
    → 必要时展开原始会话或证据
```

例如“测试页面打不开”可以先用错误码、页面地址检索，再通过语义相似度寻找“访问测试环境需要代理”的经验。主机范围应根据问题分别查询：本机配置和开发机服务状态可能同时相关。

对于本次任务直接引用的记忆，应按 ID 读取，避免完全依赖 Top-K 搜索。“语义相近”“最新写入”“已验证有效”是不同属性，排序分数不能替代有效性判断。

## 跨机器共享：中心服务与副本同步

| 方案 | 工作方式 | 主要代价 |
| --- | --- | --- |
| 中心服务 | 两台机器通过 API 或 MCP 访问同一份权威数据 | 需要网络可达和服务可用 |
| 本地副本 | 两边本地读写，通过同步协议交换变更 | 要处理延迟、冲突和删除传播 |

两台机器的小规模协作可以先采用中心服务，也可以使用一份权威交接文件和分别写入的结果文件。若采用副本模式，需要稳定 ID、版本信息和冲突策略。不要把运行中的 SQLite 文件当普通文档直接双向同步，应使用应用层同步或一致性备份机制。

无论选哪种方式，项目身份都应独立于绝对目录：同一项目在两台机器上的路径往往不同。凭据也不应写进共享交接正文；执行者通过各自获准使用的凭据来源获取。

## 社区组件各自解决什么

| 组件 | 主要能力 | 接入时需要明确的边界 |
| --- | --- | --- |
| cass | 通过 SSH/rsync 汇集并索引不同机器的 Agent 会话 | 历史可搜索后仍需主动读取 |
| Beads | 任务、依赖、状态和项目记忆 | 数据同步与全局任务互斥要分别设计 |
| MCP Agent Mail | 身份、消息线程、回执和协作记录 | 消息送达后仍需有执行者处理 |
| mcp-memory-service | 记忆持久化、索引和检索 | 需配置写入触发及失效知识治理 |
| Multica | 共享工作记录、运行调度和 daemon 执行 | 原生会话恢复受运行环境限制 |

这些是可组合的实现路径，不能仅凭项目活跃度认定已满足某个环境的可靠性要求。cass 的远程来源机制见 [会话检索项目](https://github.com/Dicklesworthstone/coding_agent_session_search)；Agent Mail 的消息模型见 [项目说明](https://github.com/Dicklesworthstone/mcp_agent_mail)。

## Multica：从共享记录到实际执行

已有的 [Multica 控制面概览](./multica-agent-control-plane.md) 讨论选型和管理层定位；这里聚焦上下文交接机制。

### 中心服务与本机 daemon

Multica 的中心服务使用 PostgreSQL 保存协作数据。Agent 表示身份与执行配置，Runtime 表示机器上的具体工具环境，Run 表示一次执行。各机器上的 daemon 连接服务端、领取任务并调用本机 Agent 工具。参见 [架构说明](https://github.com/multica-ai/multica#architecture)。

```text
Web / Desktop
      │
Multica Server ── PostgreSQL
      │
      ├── Linux daemon ── 开发 Agent
      └── Desktop daemon ── 本机 Agent
```

服务端保存 issue、评论、配置、run 上下文和结果，不会自动上传完整工作目录。daemon 通过持久连接接收任务通知，轮询用于补查，心跳用于确认可用性。自定义环境变量和 MCP 配置可能保存在服务端；本地执行并不意味着全部数据和凭据都只在本机。参见 [Daemon 与数据边界](https://multica.ai/docs/daemon-runtimes)。

### 执行记录上报

源码中的 `executeAndDrain` 收集 Agent 输出流，将文本、工具调用、工具结果和错误转换为带 `seq` 与类型的消息，再批量上报。序号用于按顺序重建执行日志；同一次 run 的重试继续递增。部分工具结果会被截断，所以平台日志不能直接等同于完整原生 transcript。参见 [daemon 实现](https://github.com/multica-ai/multica/blob/main/server/internal/daemon/daemon.go)。

Run 的执行状态与 Issue 的业务状态分别管理。一次执行正常退出不代表任务验收通过，后续讨论仍可产生新的 run。参见 [Runs 文档](https://multica.ai/docs/tasks)。

### 接手时怎样重新获得上下文

Multica 的 `BuildPrompt` 会给出确定的 issue ID，并引导 Agent 先读 issue，再扫描评论摘要和展开相关线程：

```bash
multica issue get <issue-id> --output json
multica issue comment list <issue-id> --roots-only --summary --compact --output json
multica issue comment list <issue-id> --thread <thread-id> --tail 30
```

因此，任务上下文重建主要依赖 ID、线程和增量信息。源码对首次接手、成功恢复会话、恢复上下文存在缺口等情况采取不同提示策略。这条路径不要求先将 issue 全部向量化。参见 [提示词构建实现](https://github.com/multica-ai/multica/blob/main/server/internal/daemon/prompt.go)。

### 原生会话恢复的限制

Multica 还使用原生 session 标识尝试 resume。Codex 恢复前会检查本地 rollout 是否存在，无法恢复时转为新会话并说明上下文缺口。共享 issue 可用于重建工作背景，但不能据此推断原生会话文件已跨机器完整同步。参见 [恢复逻辑](https://github.com/multica-ai/multica/blob/main/server/internal/daemon/daemon.go)。

已有 run 绑定其 Runtime；机器离线不会自动把该 run 搬到另一台机器。跨机器协作应面向目标 Runtime 创建新的执行，并共享 issue 或明确交接说明。目标环境也必须配置所需浏览器或桌面工具，启动某个 Agent CLI 不代表自动继承同品牌桌面应用的全部能力。参见 [任务分配与执行边界](https://multica.ai/docs/assigning-issues)。

## 最小交接方案与验证方法

对于开发机加本机的场景，可以先实现以下顺序：

1. 远端写入交接记录：任务 ID、目标、本机待办、关键依据、验收条件、版本和状态。
2. 本机按 ID 读取任务，直接加载关联证据，缺背景时再查会话或长期记忆。
3. 本机领取任务，执行操作，记录实际变化和验证结果。
4. 远端确认结果后继续工作，把有复用价值的结论另存为长期记忆。
5. 手动交接稳定后，再增加 daemon、通知和自动唤醒。

建议用以下案例验证，本文尚未实际执行这些验证：

| 验证案例 | 应观察到的结果 |
| --- | --- |
| 全新会话接手 | 仅凭任务 ID 能找到目标、待办和证据 |
| 两个执行者同时领取 | 同一个权威任务只被一个执行者领取 |
| 操作成功后回报断线 | 恢复后先核实效果，避免重复修改 |
| 旧配置被新结论替代 | 检索能识别替代关系，当前任务引用正确版本 |
| 换机器且原生会话不存在 | 明确报告恢复缺口，通过记录补足背景 |
| 目标机器缺少工具 | 说明缺失能力，任务不被误报为完成 |

## 常见错误与适用边界

- **把“已存储”当成“模型已知道”**：需要显式读取或上下文注入触发。
- **让向量搜索决定任务是否完成**：完成状态应精确读取，并有验收证据。
- **把消息送达当成 Agent 已启动**：空闲客户端仍需要能接收并执行工作的程序。
- **把 session ID 当成全部会话**：恢复还依赖原生数据、运行环境和工具支持。
- **把历史日志当成当前事实**：记录可能过期、截断，操作前应核实相关环境。
- **把模型生成的总结直接当作已验证知识**：应保留来源，区分观察、推断和建议。

系统规模尚小时，结构化交接记录和明确读写流程已经能解决大量上下文断层。历史检索、长期记忆和调度平台应根据实际缺口逐步增加，并分别验证状态正确性、检索质量和执行可靠性。
