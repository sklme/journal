# 使用 VitePress 搭建个人知识站

## 要解决的问题

开发、排障和技术讨论会产生大量临时信息。直接保存完整过程不仅难以复用，还容易混入业务背景、内部名称和原始日志。更合适的方式是从实践中提取稳定结论，再按技术主题组织为知识文章。

知识站需要同时满足三个目标：

- 文章按主题组织，可以持续修订。
- 本地与持续集成使用同一套构建检查。
- 所有内容在进入 Git 历史前完成脱敏和人工复核。

## 核心设计

使用 TypeScript 配置 VitePress，把 Markdown 编译为静态页面。知识文章按实际内容形成主题目录，分类下直接展示文章；不预先创建空分类，也不为每次开发活动创建按日期排列的过程日志。

```text
实践素材
  → 提取可复用结论
  → 按主题编写知识文章
  → 敏感信息检查
  → TypeScript 类型检查
  → VitePress 构建
```

Git 提交记录内容的修改历史，文章本身只保留理解主题所需的问题、原理、方案、边界和常见错误。

## 最小目录结构

```text
docs/
├── knowledge/
│   ├── ai-engineering/
│   ├── engineering/
│   └── index.md
└── .vitepress/
templates/
└── knowledge.md
```

分类首页负责列出文章，VitePress 侧边栏以二级目录展示分类及其文章。新文章优先进入已有分类，只有现有分类无法表达主题时才增加新分类。

## 内容安全

仓库内容按照可能公开到互联网的标准管理：

1. 原始工作日志和截图不进入仓库。
2. 示例使用公开占位符，并重新编写为最小示例。
3. Git hook 在提交前扫描暂存文件。
4. 持续集成再次扫描全部文件并执行生产构建。
5. 自动扫描通过后仍需人工复核。

## 验证方法

本地执行以下命令，运行敏感信息扫描、TypeScript 类型检查和 VitePress 生产构建：

```bash
pnpm check
```

检查成功只代表规则扫描和工程构建通过，不代表内容一定适合公开。文章是否包含受限制信息，最终仍需要作者判断。

## 适用边界

这种结构适合少量作者维护、以长期复用为目标的技术知识库。若主要目标是日报、工时记录或项目进度追踪，应使用专门的工作日志系统，不应把过程流水混入知识文章。

## 常见错误

- 按日期保存所有开发过程，导致同一主题分散在多篇文章中。
- 只记录最终命令，没有解释原理和适用条件。
- 把原始日志或内部代码直接作为示例。
- 依赖自动扫描替代人工保密判断。
