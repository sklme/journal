# AKSK、STS 与 CAM 角色：三种临时凭证获取方式

## 要解决的问题

服务为什么可以不保存长期云密钥，却仍能访问私有对象存储？OIDC、SAML、CAM 角色和 STS 分别负责哪一步？拿到临时 token 后，为什么还需要签名？

访问资源需要分别回答三个问题：**调用者是谁、允许做什么、用什么凭证发请求**。本文以腾讯云 COS 为例，将身份认证、权限授权、凭证签发和资源请求分开理解。

这里的“三种方式”按申请 STS 时的身份依据划分：AKSK、OIDC、SAML，并非 STS 接口的完整枚举。托管平台一节是通用架构示意，不代表某个具体系统的实现。本文未申请真实凭证、修改云端策略或执行资源访问。

## 核心概念

| 概念 | 含义 | 在链路中的作用 |
| --- | --- | --- |
| AK / Access Key ID | 密钥标识，腾讯云通常称 SecretId | 指定使用哪一把密钥 |
| SK / Secret Key | 秘密密钥，腾讯云通常称 SecretKey | 在调用方计算请求签名 |
| STS | Security Token Service，安全凭证服务 | 签发有权限范围和有效期的临时访问凭证 |
| STS 临时凭证 | 临时 ID、临时密钥、安全令牌三元组 | 供 SDK 构造资源请求 |
| CAM | Cloud Access Management，访问管理 | 管理身份、角色与授权策略 |
| CAM 角色 | 可由受信任主体扮演的虚拟身份 | 关联信任条件与资源权限 |
| IdP | Identity Provider，身份提供商 | 认证用户或工作负载，签发身份证明 |
| OIDC / SAML | 联合身份协议 | 让云端验证外部身份系统出具的证明 |

### AKSK 与账号、桶的关系

云端创建的 API 密钥关联云身份，权限来自适用的授权策略。密钥不是从桶名或对象路径推导出来的，也不能从 AK 推导 SK。“长期”表示它不像 STS 凭证一样具有短期到期机制，并不表示不能禁用、删除或轮换。

AK 会随请求发送，单独持有它不能完成认证；SK 必须保密。AK/SK **不是非对称密码学中的公钥与私钥对**。AK 负责标识，SK 参与 HMAC 计算；AK 本身不能用来验签。这与 IdP 用私钥签名、接收方用公钥验证身份证明的机制不同。

下面只是逻辑模型，不代表云平台内部的数据库或密钥存储实现：

```text
SecretId → 云身份、密钥验证信息、启用状态
云身份   → 适用的操作权限、资源范围和授权条件
```

密钥标识也没有必要主动公开。完整请求签名和预签名 URL 可能在有效期内被使用，不能因为没有明文 SK 就视为无敏感信息。

### STS token 到底有几项

| 常见字段 | 含义 |
| --- | --- |
| TmpSecretId | 临时密钥 ID |
| TmpSecretKey | 临时签名密钥 |
| Token / SecurityToken / SessionToken | 配套安全令牌，名称依 API 或 SDK 而异 |
| ExpiredTime | 到期信息，是元数据，不是第四把密钥 |

口头上的“STS token”可能指整个三元组，也可能只指其中的安全令牌。接入时必须看字段，不能凭简称判断。COS SDK 使用临时密钥计算签名，并传递配套安全令牌，不能把单独的 token 当作通用 Bearer Token 填入请求。

字段和 SDK 返回结构见[临时密钥生成及使用指引](https://cloud.tencent.com/document/product/436/14048)。

## CAM 角色：谁能使用，与使用后能做什么

可以把角色理解成一个岗位。以一个通用的对象上传角色为例：

| 配置 | 示例职责 |
| --- | --- |
| 信任策略 | 只允许指定 IdP 中满足主体条件的发布任务扮演角色 |
| 权限策略 | 只允许上传指定桶的 `artifacts/` 前缀，不授予删除权限 |
| RoleArn | 选择目标角色的标识，本身不是凭证 |
| 角色会话 | 成功扮演角色后的一次临时使用实例，持有 STS 凭证 |

信任策略回答“谁可以使用角色”，权限策略回答“使用后允许做什么”。知道角色名称仅能提出申请，STS 仍要验证身份和信任条件；资源访问还要通过适用的资源策略等检查。

角色配置是长期存在的授权对象，角色会话凭证是有期限的运行时结果。角色没有长期 AKSK，也不能把角色对象称为 token。参见[创建角色](https://cloud.tencent.com/document/product/598/19381)。

## 方式一：使用 AKSK 申请 STS

### 可信后端直接申请

```text
可信后端持有长期 AKSK
    │ 用 SK 对 STS 请求签名，指定申请范围和期限
    ▼
STS 验证申请者与授权
    │ 签发临时 ID + 临时密钥 + Token + 到期信息
    ▼
获授权的程序通过 SDK 访问 COS
```

`GetFederationToken` 是常见接口；也可以由已认证云身份调用 `AssumeRole` 获取角色凭证，后者增加了目标角色和角色信任检查。因此不能把所有 AKSK 申请都描述为“必须先创建角色”。申请策略可以缩小临时授权范围，不能凭空增加原本没有的权限。

### 通过凭证代理集中托管

当多个应用都需要访问云资源时，可以由可信的凭证代理管理长期密钥。应用先向代理证明自身身份，代理检查授权后申请或复用仍然有效的临时凭证。

```text
业务服务 → 凭证代理 → 云 STS
           校验调用者   签发临时凭证
           与授权范围
业务服务 ← 临时凭证 ← 凭证代理
    │
    └─ 用临时凭证访问 COS
```

这是两段不同的认证：业务服务到代理使用平台认可的服务身份；代理到 STS 使用云端认可的密钥认证。业务不持有长期云 AKSK，并不意味着整个系统不再使用长期 AKSK。

资产名、应用名等选择标识不能代替身份认证。代理还应限制调用者可以申请的动作、资源与期限，不能无条件相信调用方传入的策略。代理自身的组织、资产和应用对象也不自动等于 CAM 角色。

这种架构减少长期密钥在业务中的分发范围，但代理自身仍需可靠的密钥管理、授权控制和审计。缓存期限、刷新窗口和频控属于具体平台契约，不能推广成 STS 的统一规则。

## 方式二：OIDC 身份令牌换角色凭证

OIDC 在 OAuth 2.0 上增加身份认证层。用户登录场景中，ID Token 使用 JWT 表达身份声明；工作负载联合身份也可以使用平台签发且被云端接受的 OIDC 令牌。

| 声明 | 作用 |
| --- | --- |
| `iss` | 谁签发令牌 |
| `sub` | 令牌代表哪个主体 |
| `aud` | 预期接收方 |
| `exp` | 到期时间 |

JWT 只是格式。手写相同字段的 JSON、任意网站的 JWT 或普通 OAuth Access Token，都不会自动成为可换取云角色凭证的身份证明。身份接收方需要检查来源、签名、有效期和上下文条件。协议定义见 [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html)。

### 先建立信任，再运行换票

管理员先配置 OIDC 提供商、颁发者、audience 和验签信息，再配置角色信任与资源权限。信任条件应尽可能限定到预期主体，而不是接受同一提供商下的任意身份。

运行时的流程为：

1. 用户向 IdP 登录，或工作负载通过运行平台获得身份令牌。
2. 程序携带有效 OIDC 令牌和目标角色调用 `AssumeRoleWithWebIdentity`。
3. STS 验证令牌及角色信任条件，成功后签发角色临时凭证。
4. 程序用临时三元组通过 COS SDK 访问资源。

OIDC Token 和 STS 凭证有各自的有效期。COS 消费的是后者，再次换票需要满足前者的时效和信任条件；STS 到期不必然意味着用户必须重新输入密码。

### 主要输入字段

| 字段 | 含义 |
| --- | --- |
| ProviderId | 云端配置的 OIDC 提供商名称 |
| WebIdentityToken | 受信任 IdP 或平台签发的真实令牌 |
| RoleArn | 目标角色 |
| RoleSessionName | 会话名称，用于区分会话，不是身份凭证 |
| DurationSeconds | 期望的临时凭证时长，受接口规则约束 |

[AssumeRoleWithWebIdentity](https://cloud.tencent.com/document/product/1312/73070) 不要求调用方用长期云 AKSK 签名。官方 V3 调用说明要求 `Authorization: SKIP`，无需 `X-TC-Token`。这并不是免认证：认证依据是提交的联合身份令牌。应按该接口和所用 SDK 的说明配置调用。

工作负载仍然需要上游身份基础。例如容器平台可为 Pod 投影 ServiceAccount Token；角色提供商、主体条件和运行平台关联配置正确后，程序才能换取云凭证。不能假设任何机器都能匿名领取有效令牌。参见 [TKE 工作负载身份示例](https://cloud.tencent.com/document/product/457/132413)。

## 方式三：SAML 身份断言换角色凭证

SAML 常用于企业联合登录。IdP 以签名 XML 断言表达认证结果和身份属性。接入时需要在云端配置 IdP 的元数据与验签信息、角色信任和权限，并在 IdP 侧配置服务提供方及所需属性。

```text
用户 / 客户端 → IdP 完成认证
                   │ 签发 SAML 断言
                   ▼
客户端携带断言、提供商与目标角色 → STS
                                  │ 验证后签发角色凭证
                                  ▼
                             客户端访问 COS
```

`AssumeRoleWithSAML` 的主要字段如下：

| 字段 | 含义 |
| --- | --- |
| SAMLAssertion | 按接口要求 Base64 编码的 SAML 断言 |
| PrincipalArn | 云端 SAML 身份提供商标识 |
| RoleArn | 目标角色标识 |
| RoleSessionName | 角色会话名称 |
| DurationSeconds | 期望的临时凭证时长 |

Base64 只是编码，既不加密也不证明身份。信任来自断言签名、有效条件与预先配置的提供商和角色关系。员工姓名、登录 Cookie 或手写 XML 不能代替有效断言。

[AssumeRoleWithSAML](https://cloud.tencent.com/document/product/1312/48196) 的 V3 调用同样使用 `Authorization: SKIP`，无需 `X-TC-Token`；成功后返回临时三元组与到期信息。SAML 也可用于控制台 SSO，但控制台登录态与 COS SDK 所用凭证是两个对象。上游是否要求 MFA、如何续期由 IdP 的认证流程决定。

## 三种方式如何选择

| 对比项 | AKSK，包括凭证代理 | OIDC | SAML |
| --- | --- | --- | --- |
| 申请 STS 的身份依据 | 云身份密钥签名 | 受信任的 OIDC 令牌 | 受信任的 SAML 断言 |
| 常见证明形式 | 请求签名 | 签名 JWT | 签名 XML |
| 此申请方式是否依赖长期云 AKSK | 直接申请者或代理持有 | 调用方不需要 | 调用方不需要 |
| 是否必然涉及角色 | 取决于接口 | 是 | 是 |
| 主要前提 | 云权限；代理模式还需调用者与资产授权 | 提供商、验签信息、角色信任与权限 | 提供商元数据、断言配置、角色信任与权限 |
| 常见场景 | 可信后端、已有凭证托管体系 | 应用、容器、流水线身份 | 企业联合登录及配套工具 |
| 最终供 COS 使用的凭证 | 临时三元组 | 临时三元组 | 临时三元组 |

选择依据是运行环境能可靠提供什么身份证明，以及现有身份系统如何建立信任。OIDC 和 SAML 的差异不只在 JSON 与 XML，不能仅凭格式选型。

## 拿到 STS 后，COS 请求如何签名

### 长期 AKSK 可以直接访问

可信程序可以直接用长期密钥对 COS 请求签名，并不必须先经过 STS。匿名访问公开对象是另一种情况，这里讨论需要鉴权的请求。

简化地说，签名依赖秘密、规范化请求和时间范围。COS 的算法还包含中间密钥与请求摘要：

```text
SignKey      = HMAC-SHA1(SecretKey, KeyTime)
HttpString   = 规范化的方法、路径、参与签名的参数与请求头
StringToSign = "sha1\n" + KeyTime + "\n" + SHA1(HttpString) + "\n"
Signature    = HMAC-SHA1(SignKey, StringToSign)
```

这里省略排序、编码与十六进制格式等细节，只用于解释。生产实现应使用 SDK，完整规范见 [COS 请求签名](https://intl.cloud.tencent.com/zh/document/api/436/7778?lang=zh)。该算法不能直接套用于 STS 云 API 3.0 的 TC3 签名。

HMAC 证明秘密持有并保护纳入签名的信息完整性，不加密文件；传输保密性由 HTTPS 等机制提供。云端需要相应秘密或等效的受控验证能力，不能仅靠 AK 验证签名。

### STS 增加凭证签发阶段，没有取消签名

| 环节 | 长期密钥直接访问 | STS 临时凭证访问 |
| --- | --- | --- |
| 标识密钥 | SecretId | TmpSecretId |
| 在调用方计算签名 | SecretKey | TmpSecretKey |
| 携带配套安全令牌 | 不需要 STS token | 需要 Token |
| 生命周期 | 可禁用、删除或轮换 | 有明确的到期时间 |

下面是临时凭证请求的占位示意。`...` 省略必需签名参数，域名是占位符，不能直接执行：

```http
GET /artifacts/demo.zip HTTP/1.1
Host: example.com
Authorization: q-ak=<TMP_SECRET_ID>&...&q-signature=<SIGNATURE>
x-cos-security-token: <TOKEN>
```

临时 SK 留在签名程序中，不作为 COS 请求字段发送。长期 AKSK 申请模式中，先用长期 SK 认证 STS 请求，再用临时 SK 签名 COS 请求，这是两次不同的认证。OIDC / SAML 替换的是前一次认证依据，后续资源访问仍需要临时凭证签名。

STS 临时凭证不是将长期密钥截短，也不是业务随意生成的字符串。它与获授权身份或会话、权限和有效期关联。不要推断这些信息一定明文包含在 token 中，也不要猜测云端如何存储临时密钥；业务应将 token 视为不透明凭证。

请求有签名并不表示所有自定义头或整个文件正文都自动纳入保护，具体覆盖范围依签名及 API 校验规则而定。拿到一个有效签名不等于拿到 SK，但原请求可能在有效期内被重放。

### 刷新凭证与下载方式

按返回的过期时间管理凭证，使用 SDK 支持的刷新机制或在到期前重新申请。不要假定所有 STS 凭证都固定一小时，也不要将某个平台的缓存刷新窗口当成云 API 规则。

| 下载方式 | 下载者需要什么 |
| --- | --- |
| SDK 访问私有 COS | 有效且获授权的凭证，以及桶、地域、对象键等参数 |
| 使用预签名 URL | 完整且仍然有效的 URL，不必另外领取整组三元组 |
| 通过 CDN 下载 | 满足 CDN 的用户鉴权；CDN 回源 COS 是另一段授权 |

预签名 URL 没有把对象改成公有读，也不应该包含 SecretKey。其可用性还受到签名和所用凭证有效期等条件约束。关于 CDN 与源站的边界，参见 [CDN 与 COS：CNAME、TLS、回源路径和权限](./cdn-cos-cname-tls-origin-pull.md)。

## 适用边界与排查顺序

最小权限需要同时落实到动作、资源与期限。只上传某个前缀时，不应默认申请所有操作与所有资源。申请成功也不能证明任意桶、任意对象或任意动作都获授权。

按身份进入系统的顺序排查：

1. 确认实际使用的凭证获取方式和资源配置。
2. 代理模式检查调用者认证与授权；联合身份模式检查提供商、签名、有效期和主体条件。
3. 检查目标角色是否正确，信任策略与资源权限是否匹配。
4. 确认返回的三元组完整、未过期，SDK 字段映射正确。
5. 检查 COS 的桶、地域、对象键、动作、签名时间和适用策略。

诊断记录保留错误码、请求 ID 和检查结论即可，不记录真实密钥、令牌或完整预签名 URL。具体有效期上限、提供商接入方式和 SDK 参数以当前官方文档为准。

## 常见错误

- **把 STS token 当成单独的万能令牌。** 安全令牌与请求签名承担不同作用，SDK 通常需要完整三元组。
- **认为获取 STS 总要提供长期 AKSK。** OIDC / SAML 换票接口使用受信任的外部身份证明。
- **认为不用 AKSK 就不用认证。** 认证转移到上游身份系统、令牌验证和角色信任检查。
- **把角色名、资产名或应用名当凭证。** 标识只能选择对象，不能证明调用者身份。
- **把平台自己的服务认证当成 OIDC。** 云端只接受预先建立信任并符合接口契约的证明。
- **认为 STS 到期必然要求重新交互登录。** 是否需要用户操作取决于 IdP 会话与运行平台续发能力。
