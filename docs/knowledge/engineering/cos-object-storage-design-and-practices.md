# COS：对象存储的设计、权限与工程实践

## 要解决的问题

COS（Cloud Object Storage）常被当成“云上的文件夹”使用，但它的设计更接近一个通过 HTTP API 访问的对象存储系统。理解 Bucket、Object、ObjectKey、身份、策略和访问域名之间的关系，才能正确设计上传、下载、分发、归档和多租户隔离。

本文以腾讯云 COS 的概念为例，提炼对象存储中较通用的设计思想。控制台字段、策略动作和计费规则以厂商文档为准。

## 1. 先建立整体模型

COS 的资源层级可以简化为：

```text
主账号
└── Region 地域
    └── Bucket 存储桶
        └── Object 对象
            ├── ObjectKey 对象键
            ├── 内容
            └── 元数据
```

### Bucket 是管理边界

Bucket 是对象的容器，也是很多配置的边界。它具有所属账号、地域、访问域名和访问策略，并可以配置生命周期、版本控制、加密、日志、事件通知、跨地域复制和 CDN 等能力。

地域一旦选定，数据的物理位置、访问延迟、合规范围和部分费用就基本确定。通常先按业务主要访问区域选择地域，再决定是否使用多 AZ 或跨地域复制。

### Object 是存储基本单元

每个对象由 `ObjectKey`、内容和元数据组成。ObjectKey 是对象在 Bucket 内的唯一标识，例如：

```text
tenant-a/releases/2026-09/app.js
```

COS 没有传统文件系统意义上的目录。`tenant-a/` 和 `releases/` 只是 ObjectKey 的前缀，控制台把前缀展示成文件夹。对象的访问地址通常由 Bucket 域名和 ObjectKey 拼接而成。[对象概述](https://cloud.tencent.com/document/product/436/13324)

这带来两个实践结论：

- 目录权限通常通过 ObjectKey 前缀表达，而不是给一个真实目录加权限。
- “改名”通常是复制到新的 ObjectKey，再删除旧对象，不能把它当成文件系统的原子 rename。

### COS 是数据面，不是业务权限中心

COS 负责保存和读取对象。业务系统仍然需要决定：哪个用户能看到哪个文件、文件属于哪个租户、链接有效多久、删除是否需要审批。COS 的策略负责执行这些决定，不能替代业务的授权模型。

## 2. 权限系统：身份、资源和动作

一次 COS 请求可以拆成三个问题：

```text
请求者是谁？
要访问哪个资源？
要执行什么动作？
```

### 身份认证

常见请求者包括：

- 主账号和 CAM 子账号
- CAM 角色
- 其他主账号
- 腾讯云服务身份，例如 CDN
- 匿名用户

请求可以使用永久密钥签名、临时密钥、预签名 URL 或腾讯云服务身份。永久密钥适合受控的服务端环境；前端直传、临时下载和临时处理应使用有效期和权限范围都受限的临时凭证。[临时密钥](https://intl.cloud.tencent.com/zh/document/product/436/14048)

### 三类授权方式

| 授权方式 | 绑定位置 | 主要回答的问题 | 适合场景 |
| --- | --- | --- | --- |
| CAM 用户策略 | 用户、用户组或角色 | 这个身份能调用哪些 API | 给运维账号、业务服务账号授权 |
| Bucket Policy | 存储桶 | 这个资源允许谁对哪些对象做什么 | 前缀权限、跨账号、匿名访问、CDN 服务授权 |
| ACL | Bucket 或 Object | 某个资源有哪些简单的读写授权 | 简单兼容场景，复杂策略不推荐依赖它 |

CAM 用户策略是身份侧授权；Bucket Policy 是资源侧授权。Bucket Policy 使用 JSON 描述资源、动作、主体和允许或拒绝条件，可以覆盖 Bucket、对象或对象前缀，并支持向云服务和其他账号授权。[存储桶策略](https://cloud.tencent.com/document/product/436/18031)

### 权限评估的思路

COS 收到请求后，先认证请求身份，再综合 CAM 策略、Bucket Policy 和 ACL 评估。设计时应遵守：

1. 默认私有。
2. 只授予必需动作，例如只读服务不要授予删除权限。
3. 用 ObjectKey 前缀隔离租户、业务和环境。
4. 高风险动作使用显式拒绝或额外审批。
5. 让服务账号和操作人员使用不同身份。

“给 CDN 读权限”和“给负责配置 CDN 的子账号读权限”是两件事。前者是运行时服务身份授权，后者是控制台管理权限；两者不能互相替代。

### 公有读与私有读

- **公有读**：匿名用户可以直接执行读取对象的请求。适合真正公开的资源，但知道 COS 源站地址的人也可能绕过 CDN 下载。
- **私有读**：匿名请求不能读取对象，必须使用有权限的身份、临时签名或被授权的云服务。

“私有读”不等于“不能通过 CDN 访问”。常见的安全分层是：COS 保持私有，授权 CDN 服务身份回源，再单独决定 CDN URL 是否需要用户鉴权。COS 回源鉴权解决的是 CDN 能不能读源站；CDN 鉴权解决的是最终用户能不能读 CDN 地址。

## 3. 主要操作及适用场景

### 对象操作

| 操作 | 作用 | 常见场景 |
| --- | --- | --- |
| `PutObject` | 上传对象 | 图片、附件、构建产物 |
| `GetObject` | 下载对象 | 文件读取、CDN 回源 |
| `HeadObject` | 获取元数据 | 大小、类型、更新时间、校验 |
| `DeleteObject` | 删除对象 | 用户删除、清理临时文件 |
| `ListObjects` | 列举对象 | 文件列表、前缀扫描 |
| `CopyObject` | 复制对象 | 版本发布、归档、改名 |

小文件可以直接上传。大文件使用分块上传：先初始化任务，再上传多个分块，最后提交合并。分块上传支持并行、断点续传和失败重试，适合视频、安装包和备份文件。[上传对象](https://cloud.tencent.com/document/product/436/65935)

### Bucket 管理操作

Bucket 层常见配置包括：

- 权限、Policy、ACL 和 CORS
- 生命周期和版本控制
- 加密、日志和事件通知
- 跨地域复制和多 AZ
- 静态网站、自定义域名和 CDN

这些配置影响整个资源边界，不应由普通业务上传账号随意修改。

### 存储类型和生命周期

标准存储适合高频在线访问；低频、归档和深度归档适合访问较少的历史数据。冷存储通常有取回费用、最短存储时间或恢复延迟，不能只按容量单价选择。[存储类型概述](https://intl.cloud.tencent.com/zh/document/product/436/30925)

常见生命周期策略是：

```text
近期文件：标准存储
长期不活跃文件：低频或归档
超过保留期：自动删除
```

生命周期规则应结合合规保留期、恢复需求、最小存储时长和删除成本一起评估。

## 4. COS、CDN 与访问域名

COS 是源站存储，CDN 是缓存和分发层：

```text
用户 → CDN 边缘节点
          ├── 命中缓存：直接返回
          └── 未命中：请求 COS → 返回并缓存
```

CNAME 只负责把业务域名接入 CDN 调度系统；它不负责读取 COS，也不等于回源。回源是 CDN 以独立的 HTTP/HTTPS 请求访问 COS 源站。

普通配置下，用户 URL 的路径会映射到 COS 的 ObjectKey。例如：

```text
用户请求：/assets/app.js
COS 对象：assets/app.js
```

如果业务 URL 和 COS ObjectKey 不一致，就必须显式配置路径重写或高级回源规则。CDN 不会自动猜测项目目录、版本目录或租户目录。

CDN 相关权限至少分为两段：

```text
用户 → CDN：是否允许访问分发地址？
CDN → COS：CDN 是否有权读取源对象？
```

使用私有 COS 作为 CDN 源站时，通常需要给 CDN 服务身份授予对象读取相关权限，并在 CDN 开启对应的回源鉴权。公开分发还是受限下载，再由 CDN 访问鉴权控制。[COS CDN 加速](https://intl.cloud.tencent.com/zh/document/product/436/18669)

### 4.1 公开地址、预签名 URL 与临时密钥

需要把“对象地址”和“访问凭证”分开理解：

| 方式 | URL 形态 | 是否需要请求签名 | 适用场景 |
| --- | --- | --- | --- |
| 公有读对象地址 | 普通对象 URL | 否 | 真正公开的资源 |
| 预签名 URL | 对象 URL 加签名参数 | 是 | 单个文件的临时上传或下载 |
| 临时密钥 | 客户端持有短期密钥并自行签名 | 是 | 多个文件、浏览器直传、客户端 SDK |
| CDN 鉴权 URL | CDN 域名加 CDN 签名参数 | 由 CDN 校验 | 通过 CDN 受限分发 |

因此，**私有读 COS 没有不带鉴权、面向所有人的永久公开 COS URL**。对象的普通 URL 仍然可以拼出来，但匿名请求会被 COS 拒绝。私有对象通常通过后端代理、COS 预签名 URL、临时密钥或 CDN 服务身份访问。

预签名 URL 是把访问对象、HTTP 方法和有效时间纳入签名后生成的地址。拿到 URL 的人可以在有效期内使用它，所以它更像一个“带时效的持有者凭证”，而不是用户身份本身。使用临时密钥生成预签名时，实际有效期取签名有效期和临时密钥有效期中较短的一个；使用永久密钥虽然可以生成更长时间的签名，但泄露后的影响范围也更大。[预签名 URL](https://cloud.tencent.com/document/product/436/45243)

常见下载流程是：

```text
用户请求下载
    ↓
后端验证用户权限
    ↓
后端生成指定 ObjectKey 的短期预签名 URL
    ↓
用户直接访问 COS
```

如果客户端需要连续上传多个文件，后端可以发放限制到某个 Bucket、前缀、操作和时间范围的临时密钥，让客户端用 SDK 自行签名请求。不要把永久密钥放入网页、移动端包或日志中。[临时密钥](https://cloud.tencent.com/document/product/436/14048)

COS 预签名 URL 和 CDN 鉴权 URL 是两套机制。COS 预签名通常针对 COS 源站域名，不能直接当作 CDN 域名的鉴权参数；如果通过 CDN 受限分发，应使用 CDN 自己的 URL 鉴权。对于公开 CDN 分发，可以保持 COS 私有、授权 CDN 回源，同时关闭 CDN 用户鉴权；此时“公开”的是 CDN 地址，不是 COS 源站地址。[预签名授权下载](https://cloud.tencent.com/document/product/436/14116)

## 5. 常见架构实践

### 网站静态资源

```text
构建产物 → 上传 COS → CDN 缓存 → 用户访问
```

建议使用内容哈希或版本号命名文件，例如 `app.20260922.js`。这样发布新版本时通过新 URL 避免旧缓存污染，减少频繁刷新缓存的需要。

### 用户直传

推荐让后端先校验用户，再签发只能写入指定前缀的临时权限：

```text
用户请求上传凭证
    ↓
后端校验用户和文件类型
    ↓
签发仅允许写入 user-data/<user>/ 的临时权限
    ↓
浏览器直接上传 COS
    ↓
COS 回调或业务查询确认结果
```

这样可以减少业务服务器的带宽和内存压力，同时把租户隔离落实到 ObjectKey 和策略中。

### 私有文件下载

后端确认用户有权限后生成短期预签名 URL，或让 CDN 使用带时效的 URL 鉴权。不要把永久密钥放进网页、移动端包或日志中。

### 日志和备份

日志、备份和历史附件适合使用生命周期、版本控制、冷存储、多 AZ 或跨地域复制组合设计。需要恢复的数据，应提前验证恢复时间、取回费用和权限链路，而不是只验证“文件最终还在”。

### 多租户业务

可以通过前缀隔离：

```text
tenant-a/*
tenant-b/*
```

每个租户的临时权限只覆盖自己的前缀。如果租户之间还需要完全独立的生命周期、账单、审计或管理员边界，使用不同 Bucket 往往更清晰。

## 6. 设计检查清单

### 资源设计

- Bucket 地域是否接近主要访问者或符合合规要求？
- ObjectKey 是否包含租户、环境和版本信息？
- 是否真的需要多个 Bucket，还是前缀已经足够？

### 权限设计

- 默认是否为私有？
- 前端是否使用临时凭证而不是永久密钥？
- 上传、下载、删除、列举是否拆分授权？
- CDN 服务身份与操作人员账号是否分开？
- 是否定期检查公有读、匿名 Policy 和过宽的 `*` 资源？

### 分发和缓存

- CDN 是否只承担分发，源站是否保持私有？
- 用户 URL 与 ObjectKey 是否有明确映射？
- 查询参数是否正确参与缓存键和签名？
- 文件更新是否使用版本化 URL？

### 成本和可靠性

- 是否区分存储、请求、外网流量、回源流量和取回费用？
- 冷存储的最短存储时间和恢复延迟是否符合业务？
- 是否需要多 AZ、跨地域复制或版本保留？
- 是否有访问日志、费用告警和异常下载监控？

## 7. 常见误区

### 把 COS 当作传统文件系统

目录只是 ObjectKey 前缀，目录权限、原子 rename 和递归删除都不能直接套用本地磁盘的理解。

### 认为 CNAME 就是回源

CNAME 是 DNS 接入；回源是 CDN 到源站的请求。两者发生在不同层次。

### 只给业务子账号权限，忘了给 CDN 服务身份权限

同一主账号下的两个子账号仍然是不同的管理身份。CDN 运行时读取 COS 使用的是 CDN 服务身份，不能用“给同事子账号读权限”替代服务授权。

### COS 私有读后，CDN 自动就是私有的

COS 源站权限和 CDN 用户访问权限是两套控制。私有源站可以通过公开 CDN 地址分发，也可以要求 CDN URL 鉴权，必须根据业务目标明确选择。

### 只看存储单价

请求、外网下载、回源、数据取回、提前删除和复制都可能产生费用。容量最便宜的存储类型不一定是总成本最低的选择。

## 结论

COS 的核心思想是把“文件”拆成可寻址的对象，把存储和访问控制分离：

> Bucket 定义资源边界，ObjectKey 定义对象位置，Policy 定义谁能执行什么动作，CDN 负责缓存分发，业务后端负责最终用户授权。

只要先把这几个边界分清，上传、下载、CDN 回源、临时授权、归档和多租户隔离都可以用同一套模型推导出来。
